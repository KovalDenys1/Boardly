# Android app (Issue #1467)

Updated: 2026-10-29

The Play Store app is a Trusted Web Activity (TWA) of `https://boardly.online`, generated by
Bubblewrap. Package id `online.boardly.app`. It has no web code of its own: it opens the site in
Chrome without a URL bar, so a web release reaches Android players without a new build.

## Files

- `android/twa-manifest.json`: every setting of the app (identity, colours, start URL, icons,
  shortcuts, SDK levels, version, signing key). The only file in `android/` to edit by hand.
- `android/` (the rest): the project Bubblewrap generates from it. Do not edit; `update` deletes
  and regenerates `app/`, `gradle/` and the Gradle files in `android/`.
- `scripts/android-build.sh`, run as `npm run android:build`: the signed build (see Build).
- `public/.well-known/assetlinks.json`: ties the origin to the package (see Asset links).
- `public/manifest.json`: the web manifest, with `"id": "/"`.

## Prerequisites

- JDK 17: `brew install openjdk@17`.
- Android command-line tools in Homebrew's `share/android-commandlinetools`, with
  `tools -> cmdline-tools/latest` symlinked beside `cmdline-tools/`; Bubblewrap's path check wants
  that folder.
- Bubblewrap 1.27.0: `npm i -g @bubblewrap/cli@1.27.0`, with `~/.bubblewrap/config.json` pointing
  at the JDK and the SDK. `bubblewrap doctor` must pass.
- The upload key (see Signing key).

## Signing key

- **Keystore:** `~/.config/boardly-android/upload-key.jks`, alias `upload`, RSA 2048, valid 10000
  days, mode 600. Never commit it (`*.jks` is git-ignored).
- **Password:** one value for the keystore and the key, in the macOS login keychain as account
  `boardly`, service `boardly-android-upload`. Read it with `security find-generic-password -a
  boardly -s boardly-android-upload -w`. It is in no file.
- **Backup:** `~/Library/Mobile Documents/com~apple~CloudDocs/Keys/boardly-upload-key.jks` (iCloud
  Drive, `Keys/`). It is only the keystore: the login keychain does not sync, so a new Mac also
  needs the password, which should be copied once into a password manager.
- **Lost key:** this is an upload key. Once Play App Signing is on, Google holds the key that
  players' installs are signed with, and a lost upload key can be reset through Play Console
  support (a new key, then its fingerprint in `assetlinks.json`).
- **Never on a command line:** Bubblewrap's own signing passes the password to `jarsigner` and
  `apksigner` as arguments, where any `ps` shows it, and prints that command when signing fails.
  So the build script runs `bubblewrap build --skipSigning` and signs itself, with the password in
  the environment of the signer alone (`-storepass:env`, `--ks-pass env:`). Gradle never sees it.
  Everything the script prints still goes through a filter that replaces the password with
  `[redacted]`. Do not run `bubblewrap build` without `--skipSigning`.
- **The `~` in `signingKey.path`:** `twa-manifest.json` writes the path with `~` because the
  absolute path is machine-specific. Bubblewrap does not expand `~`, but with `--skipSigning` it
  never opens the key, and the script signs with the absolute `$HOME/.config/boardly-android/`
  path.

## Build

```bash
npm run android:build
```

Writes `android/app-release-bundle.aab` (the signed bundle for Play) and
`android/app-release-signed.apk` (for a device), both git-ignored, and prints their paths. The
script has Bubblewrap build the unsigned bundle and apk (`--skipSigning`), then signs the bundle
with the JDK's `jarsigner` and the apk with the SDK's `apksigner` (build-tools 36.1.0, the version
Bubblewrap 1.27.0 installs), using the same algorithms Bubblewrap does. The keystore password
comes from the keychain and reaches only the two signers, through the environment (see Signing
key). The script stops with a one-line hint when the keystore or the keychain item is missing, and
when `twa-manifest.json` changed since `android/` was generated (run Regenerate first; Bubblewrap
would otherwise ask, and bump the version on a yes). Gradle rewrites
`android/app/src/main/res/xml/shortcuts.xml` on every build, so the script copies that tracked file
to a temporary file first and puts it back when it exits, whether the build succeeded or failed;
it never runs git.

After signing, the script reads the apk's certificate with `apksigner verify --print-certs` and
stops unless `public/.well-known/assetlinks.json` lists that SHA-256 for the package in
`twa-manifest.json` (`scripts/android-assetlinks.ts`), since an app signed with an unlisted key
opens with a URL bar.

The first run downloads Gradle and the Android dependencies, a few minutes. The build has no native code (`unzip -l` shows no `lib/` entries), so Play's
16 KB page-size rule does not apply.

## Regenerate

```bash
cd android && nice -n 10 bubblewrap update --skipVersionUpgrade
```

Run it after any change to `twa-manifest.json`. Always pass `--skipVersionUpgrade`: without it
Bubblewrap bumps the version and rewrites the file. Running it twice must leave `git status
android/` clean.

`update` downloads every icon URL in `twa-manifest.json`, and the web manifest, from
boardly.online, so a new icon has to be live there before the update can use it.

## Versioning

- Bump `appVersionCode` in `twa-manifest.json` for every upload to Play; Play rejects a code it
  has seen. `appVersion` is the label players see.
- A web release needs no new build. Ship a new one only when `twa-manifest.json` changes (icons,
  colours, shortcuts, SDK level).

## Asset links

Chrome drops the URL bar only while `https://boardly.online/.well-known/assetlinks.json` lists the
SHA-256 fingerprint of the key that signed the installed app. Two keys sign it, so both
fingerprints belong in `public/.well-known/assetlinks.json`:

- the upload key, for the local `.apk`. It is in the file now;
- the Play app-signing key, for what Play delivers. It does not exist until the first upload: copy
  it from Play Console, Release, Setup, App integrity, add it to the same list, and release the
  file before testing the store build. This is still to do. Add it; never replace the upload-key
  line, because local and sideloaded `.apk` builds and the emulator check are signed with the
  upload key. Internal app sharing signs with a third key, shown on the same page. That page also
  offers a ready Digital Asset Links snippet to paste from.

`__tests__/public/assetlinks.test.ts` checks the shape and that the package matches
`twa-manifest.json`; `__tests__/scripts/android-assetlinks.test.ts` checks that the file lists the
upload key. The file reaches players only when it is on `main`.

A wrong or missing fingerprint shows as a URL bar at the top of the app.

## Play mode

The site runs in Play mode (no purchase path) when the head script in `lib/app-shell-script.ts`
sees one of three signals: the start URL's `utm_source=android_app&utm_medium=twa` pair, the
referrer `android-app://online.boardly.app`, or an Android user agent in `display-mode:
standalone`. It sets `<html data-app-shell="play">`, pauses AdSense ad requests
(`adsbygoogle.pauseAdRequests = 1`; the Play listing declares no ads) and stores the mark in
sessionStorage for the rest of the tab, and `isPlayApp()` in `lib/app-shell.ts` reads the attribute, then the stored mark,
then the display mode. The display mode is the only signal that survives Chrome restoring the tab
after it was killed in the background or the activity was recreated: a page reached by a full load,
such as the return from Google sign-in, comes back with sessionStorage empty and a boardly.online
referrer (#1486). A TWA reports `standalone`, Android Chrome in a tab reports `browser`, and
desktop and iOS installs are not Android. An installed Android PWA (WebAPK) counts too, which is
accepted: its users can still buy in Chrome, and once the Play listing exists the web manifest gets
`related_applications` with `prefer_related_applications` so Android Chrome offers the Play app
instead. Changing `startUrl` or `display` in `twa-manifest.json` means changing the detection too.

## Emulator check

Headless, against production, because production is what the app opens. The AVD is `boardly-36`
(API 36, Google Play image, in `~/.android/avd`); the emulator lives in the SDK's `emulator/`.

```bash
nice -n 10 "$ANDROID_HOME/emulator/emulator" -avd boardly-36 -no-window -no-audio -no-snapshot-save &
adb wait-for-device && adb install -r android/app-release-signed.apk
adb shell pm get-app-links online.boardly.app   # boardly.online: verified
adb shell am start -n online.boardly.app/.LauncherActivity
adb exec-out screencap -p > <scratch>/launch.png
adb emu kill
```

- **No URL bar** in the screenshot, and `verified` above, means the live `assetlinks.json` lists
  the key.
- **Play mode:** `adb forward tcp:9333 localabstract:chrome_devtools_remote` opens Chrome's
  DevTools endpoint; `document.documentElement.dataset.appShell` must be `play`.
- **A bot game:** Quick Play, Tic Tac Toe, Vs bots, to the result overlay. The invite button opens
  the Android share sheet with the lobby link.
- **Bars:** the header starts under the status bar and the page ends above the navigation bar.
- **Google sign-in** needs a Google account on the device, so it is checked on a real phone.

Last run 2026-10-29 with Chrome 133 on the image: all of the above passed except sign-in, which was
not run.

## Never use a WebView fallback

`fallbackType` stays `customtabs`. A WebView cannot complete Google sign-in (Google blocks
embedded browsers), so the fallback would lock players out.
